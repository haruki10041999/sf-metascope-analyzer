# Apex walker の実装方針

2026-11-23 時点の作業ツリーを調査した。実装対象は `src/analyzer/processor/Apex/walker/` 内。既存の Apex JSON を入力にし、**宣言・参照の収集、依存先の解決、実行本体内の変数解析**を単体で呼び出せる形にする。既存の依存関係の仕様は [walker の機能範囲](../../../../../docs/apex-dependency-walker-scope.md) を参照する。

初回は Apex の静的解析を実装する。walker は一時点の解析結果を受け取り、差分は引き続き既存の `makeApexUnitDiffs` を使う。LWC への展開は、Apex で解析の入出力と精度を検証した後に行う。 [Apex の既存 Diff](../diff/unit.ts#L110)

## 2. 宣言・参照と依存先の解決

### 宣言と実行本体を収集する

- 宣言ごとに名前、所有クラス、宣言位置、型、必要な修飾子を持つ。フィールドは `variants[]` の要素ごとに登録する。実行本体は、メソッド、コンストラクター、初期化ブロック、getter、setter、トリガー、匿名 Apex に同じ文解析を適用できる形で扱う。
- 本体や変数を識別する ID に、宣言の `sourceKey` を利用する。複数の変数を宣言する文では各 `VariantJson` のキーを使う。構造化された宣言は `sourceKeys.base` を使い、同じプロパティの getter と setter には区別できる ID を割り当てる。名前による照合には大小文字を正規化したキーを使い、表示には元の綴りを保持する。 [宣言の JSON 型](../../../types/apex/declaration.ts) · [キーの意味](../../../types/commons/ir.ts#L130)

### 参照を収集して照合する

- 型、`extends`・`implements`、`new`、呼び出し、フィールド・プロパティの読み書き、SOQL/SOSL/DML を収集する。呼び出しは名前に加え、レシーバー式、引数式、メンバー・文・式の位置を保持する。例えば `service.fetch().save()` の `save` は `fetch()` の戻り型を使って照合する。
- 修飾のない識別子は引数・ローカル変数の内側のスコープから探し、続いてクラスのメンバーを探す。`this.x`、`super.x`、`obj.x`、`Type.x` はレシーバーに応じて解決する。継承とオーバーロードは宣言型や引数から候補を絞り、一意に決まらなければ候補と理由を残す。
- リポジトリの宣言・オブジェクト・項目・子リレーションは、単位をまたぐ参照の解決時に入力として渡せる形にする。標準カタログに一致したときは型・オブジェクト単位の根拠として使う。例えば `Database.Batchable` と `System.Database` は別の標準型として照合し、カタログにあるメソッド名の例は補助情報とする。 [標準カタログの調査範囲](../../../../../docs/apex-standard-reference.md)
- 出力には元の参照と、解決済みの対象または `unknown`・複数候補を持つ。リポジトリ内の情報で欠落を確認できた場合に限り `missing` を使う。既存グラフへ渡す際も、候補だけの参照が確定した依存に見えないよう、変換できるものを検証する。

## 3. 変数の値遷移

`statement.ts` で `StatementJson[]` から実行本体ごとの制御フローグラフ（CFG）を作り、新規の `valueFlow.ts` で値を伝播させる。宣言時の初期化式を保持し、実行位置ごとの解析結果には **その時点の値と、到達し得る書き込み元**を持たせる。既存の visitor は構文上の情報収集に利用できる。値評価では、実行順・分岐・合流を CFG で扱う。

| 処理             | 実装方針                                                                                                                                                                                                                                       |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| スコープへの登録 | メソッド引数は本体の入口で登録する。`for` の宣言初期化、拡張 `for` の反復変数、`catch` の例外変数、型付き `when` の変数は各スコープに登録する。setter にはプロパティ型を持つ暗黙の引数 `value` を登録する                                      |
| 式の評価         | 初期化式、式文、条件、呼び出し引数、`return` などで同じ評価処理を使う。式の結果と評価後の状態の両方を返す。`=` は対象に書き込み、`+=`・`++` などは旧値も読む。`x++` は更新前、`++x` は更新後の値を式の結果にする                               |
| 分岐と合流       | `if`、三項演算子、短絡演算子は実行される経路をたどる。合流時に全到達経路の定数が一致すれば値を維持し、異なる場合や一部が不明なら `unknown` とする。代入元の集合は両方の経路から保持する                                                        |
| 終了と繰り返し   | `return`・`throw` は通常の後続文から分ける。`break`・`continue` は対象ループに接続し、ループの戻り辺では状態が収束するまで評価する。代入 ID はソース上のサイトで固定する。`try` の例外経路と `finally` への接続は独立して検証する              |
| メンバーと参照型 | フィールドやコレクション要素は、ローカル変数への再代入と別の書き込み先として表現する。フィールド初期化式は初期化時の情報として保持する。プロパティは getter・setter の呼び出しを収集し、後から戻り値と書き込みを呼び出し元へ反映できる形にする |

最初の値モデルはリテラルから得られる定数と `unknown`。`null` は確定値の一種として区別する。解析対象外の演算・呼び出し・制御構文に遭遇した場合は、影響し得る値や経路を `unknown` とし、元の式や理由を保持する。別の名前が同じオブジェクトを参照するときの更新や、getter・setter をまたぐ状態の伝播は、本体内の値解析が通った後に広げる。 [式の JSON 型](../../../types/apex/expression.ts) · [文の JSON 型](../../../types/apex/statement.ts)

`get;`・`set;` はプロパティの保存値への読み書きとして扱い、`getterContent.block`・`setterContent.block` が存在する場合は各本体を解析する。 [アクセサーの JSON 型](../../../types/apex/declaration.ts#L211)

例として `final Integer count = flag ? 1 : 0;` では、`variants[].init` にある `conditional` を評価して `count` を初期化する。`flag` が未知なら値は `unknown` で、宣言位置と初期化式から `1`・`0` の由来をたどれる。`new Account(Name = 'Example')` の `Name = ...` は、sObject の名前付き初期化と分かった場合、生成中のレコードの項目への書き込みとして扱う。 [Apex のサンプル](../../../../../docs/examples/repository/after/force-app/main/default/classes/ParserTest.cls)

## 4. クエリと追加できる解析

静的クエリは、SOQL の `FROM`・項目・関係・バインド式と、SOSL の `RETURNING` を JSON から収集する。子サブクエリは、メタデータで子リレーションを引ける場合に実オブジェクトへ解決する。DML は文と `Database` 呼び出しを同じ操作として表し、対象の型と発生位置を保持する。 [クエリの JSON 型](../../../../../docs/apex-json-types-queries.md)

動的 SOQL/SOSL は最初に、リテラル、ローカル変数、文字列連結からクエリ全体を確定できるケースを対象にする。復元した文字列を既存のパーサーで扱える形に変換し、静的クエリと同じ抽出へ渡す。復元文字列上の位置と、元の Apex の呼び出し・文字列の位置を区別する。構造を確定できない場合は呼び出しと元の引数を残す。 [動的クエリの既存方針](../../../../../docs/apex-dependency-walker-scope.md#動的-soql--sosl)

| Apex での活用先                | 目的                                                             | 処理の詳細                                                                                                     | 出力例                                                                             |
| ------------------------------ | ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 静的 SOQL/SOSL・DML の参照     | どのオブジェクト・項目を読み書きするかを知る                     | クエリ JSON の対象・項目・子リレーションを取り出す。DML の文やメソッド呼び出しは引数の型から対象を求める       | `Account.Name` の読み取りや `List<Account>` に対する `insert` を位置付きで返す     |
| 動的 SOQL/SOSL の復元          | 変数を経由するクエリの依存を見つける                             | 呼び出し時点の引数を定数伝播で評価し、復元できたクエリをパースして静的クエリと同じ処理に渡す                   | `Database.query(q)` の対象オブジェクト、列、呼び出し位置、文字列を組み立てた代入元 |
| 変数の使用箇所と代入履歴       | 変数に値が入った理由と、値の利用先を説明する                     | 変数 ID、読み取り、到達する書き込みを結び付ける。生存変数解析の結果で、後続で使われない代入も調べる            | 代入元・使用箇所の一覧、未使用ローカル変数、読み取られる前に上書きされた代入の候補 |
| データアクセスの詳しい内訳     | 実行本体ごとに、どこで何を読み書きし得るかを説明する             | 型、項目・プロパティの読み書き、SOQL/SOSL/DML を集める。現行レポートの `inLoop` を CFG の到達性と組み合わせる  | 更新項目、getter・setter 経由のアクセス、到達可能なループ内 SOQL/DML               |
| 文字列を経由するメタデータ参照 | 文字列を組み立てて指定した参照先を見つける                       | `Type.forName` や `Label.get` などの呼び出し先と引数位置を確認し、既存のリテラル向け処理に確定した文字列を渡す | クラス・カスタムラベルの参照先と、文字列の代入元                                   |
| 到達不能な文と null の経路     | 到達性やレシーバーの状態に基づいて確認箇所を絞る                 | CFG を探索し、分岐条件から到達性と値・型を絞り込む。安全ナビゲーションの経路も考慮する                         | `return` 後の到達不能文、null と絞れたレシーバーへのアクセス位置                   |
| 例外・非同期・外部接続の経路   | 通常のメソッド呼び出しに加え、例外処理や処理の引き渡し先をたどる | 例外辺と呼び出し分類を使い、例外の伝播、Queueable・Batch の対象、callout の位置を求める                        | `throw` から `catch` への経路、非同期処理へ渡すクラス、外部接続の発生箇所          |

優先するのは、代入履歴と動的クエリ・メタデータ参照の復元。読み取りと値の由来を検証しやすく、後続の解析にも同じ結果を利用できる。

## 5. 静的解析手法の一覧と採用方針

既存の構文解析で得られる JSON を使い、**構文上の事実 → 名前と型 → 実行経路 → 値と副作用**の順で解析を深める。先に名前や API を解決できる箇所は、その時点で依存参照を出せる。データフローは、動的クエリやメソッドを越える処理など、値の由来が必要な参照に活用する。

### 構文、名前、呼び出し先の解析

| 手法                    | 目的                                                            | 入力・処理の詳細                                                                                        | 得られる結果・Apex の例                                                               | 現状                                                                         |
| ----------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| AST・構文パターンの走査 | コードに現れる構造と位置を拾う                                  | 既存 Apex JSON を `kind` ごとにたどり、宣言・式・文・条件・スコープの入口を集める                       | `localVariable`、`assignment`、SOQL、DML のノードと `sourceKeys`                      | 既存 visitor と JSON 型を利用できる                                          |
| 名前解決・スコープ解析  | 参照した名前がどの宣言を指すかを特定する                        | 本体ごとのスコープとクラスのメンバー表を作り、内側から名前を照合する。宣言 ID を参照に付ける            | `this.count = count` の左辺をフィールド、右辺を引数に結び付ける                       | 変数型のスコープは一部実装済み。宣言 ID との対応を追加する                   |
| 型解析                  | 式が扱う型を求め、参照や呼び出し先の候補を絞る                  | 宣言型、リテラル、`new`、キャスト、要素型、解決済みの戻り型を使う。継承やオーバーロードの候補も照合する | `List<Account>` の `items[0]` から `Account` を得る。確定できない型は候補と理由を返す | 型名抽出はある。式・添字・戻り型までの解決を追加する                         |
| 呼び出しグラフ          | ある本体からどのメソッドやアクセサーが呼ばれ得るかを知る        | レシーバー型と引数型から、宣言・継承・オーバーロードの候補を照合する。呼び出し位置から候補へ辺を張る    | `service.fetch().save()` の `fetch`・`save` を位置付きで返す                          | 呼び出し概要と表示用シーケンス図はある。解決した候補を持つ解析結果を追加する |
| 依存参照の解析          | Apex がどの型、オブジェクト、項目、メタデータに依存するかを知る | 宣言・型・呼び出し・クエリの参照をリポジトリの定義と標準カタログに照合する。種類・位置・確度を保持する  | `Account.Name` の読み取りや `Database.Batchable` の実装を依存参照として返す           | 既存の抽出とグラフがある。詳細な型解決や未解決の理由を加える                 |

### 実行本体内の解析

| 手法                                  | 目的                                               | 入力・処理の詳細                                                                                                   | 得られる結果・Apex の例                                                                     | 現状                                                               |
| ------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 制御フロー解析（CFG）                 | 文・式がどの順序と経路で実行され得るかを表す       | `StatementJson[]` と子式を評価順に評価点へ変換する。通常、真偽、ループ、例外、終了の辺を付ける                     | `for` の本体や `continue` から更新式 `i++` へ進む経路、`return` が `finally` を経由する経路 | 表示用の処理フローはある。式単位の評価順と辺を追加する             |
| 到達性解析                            | 入口から実行が届く文・式を判定する                 | CFG を入口から探索する。条件が確定した場合は成立する辺を使う。経路が不明なら可能な辺を保持する                     | `return` の後続文や、定数条件で実行されない分岐の位置                                       | 値解析用 CFG 上で追加する                                          |
| 到達定義解析                          | ある読み取りに届き得る代入を特定する               | 定義サイト ID の集合を CFG 上で前向きに伝播する。単一ローカル変数への代入で集合を更新し、合流点では和集合を取る    | `if / else` の合流後の `x` に、両方の代入位置が届き得ることを示す                           | 初期化式の収集がある。書き込みと読み取りを結び付ける処理を追加する |
| 定数伝播                              | 使用時点で式や変数の値を確定できるか調べる         | リテラルと対応する演算を評価し、代入で得た定数を前向きに伝播する。到達可能な経路で定数が一致すれば合流後も保持する | `q` が確定した SOQL 文字列であれば、呼び出し時の文字列を返す                                | 値の伝播は未実装                                                   |
| 定義と使用の対応（def-use / use-def） | 代入の利用先と、読み取りの由来を両方向から調べる   | 到達定義を各読み取り位置に対応付け、代入側からも読み取りを引ける形にする                                           | `System.debug(x)` の `x` をどの文が書いたか、その代入がほかのどこで読まれたかを返す         | 到達定義の結果から追加する                                         |
| 生存変数解析                          | ある時点の値が、上書きされる前に必要になるか調べる | CFG を後ろ向きにたどる。後続で読み得る変数の集合を合流し、書き込みで除き、読み取りで追加する                       | 未使用ローカル変数や、読み取られる前に上書きされた代入の候補                                | メタデータの未使用分析は既存。ローカル変数向けを追加する           |
| パスを区別する解析                    | 分岐の条件を使って変数の値・型を絞る               | `x != null`、`instanceof`、定数条件などを評価して分岐辺ごとに状態を絞り、必要な地点で合流する                      | `if (a != null)` の真の枝で、書き換え前の `a` を非 null として扱う                          | 条件式や `?.` の JSON がある。辺ごとの絞り込みを追加する           |

現行の表示用フローには複数文をまとめたノードがあるため、値解析用 CFG は実行上の評価点と元の位置を保持する。Apex の動作を確認する例には、`if` の本体のほか、三項演算子、短絡評価、`for` の更新式、`finally` を含める。 [既存の処理フロー](../../../report/codeFlow.ts#L69) · [既存の呼び出しフロー](../../../report/apexCallFlow.ts#L182)

### 本体内のデータフローの実装

1. 各評価点の読み取り先・書き込み先を宣言 ID に結び付ける。`x += y` や `x++` は `x` の読み取りと書き込みを記録し、代入の右辺や入れ子の呼び出しも評価する。
2. 前向き解析では、代入が通ると該当するローカル変数の到達定義をその代入で更新する。分岐の合流では到達定義の和集合を取り、値は到達可能な経路で一致する定数を維持する。入口から到達不能な地点、値が不明な地点、値が `null` と分かっている地点を区別する。
3. 状態が変わった CFG ノードの隣接先だけを再評価する。ループは状態が収束するまで処理する。最初は代入サイト ID の有限集合と `定数 / unknown` の値を使い、到達性を別に保持する。追跡できない式の扱いも、状態の合流が収束するよう定義する。 [Clang のデータフロー解析の解説](https://clang.llvm.org/docs/DataFlowAnalysisIntro.html)
4. 収束した状態から「この読み取りに届く書き込み」と「この書き込みを使う読み取り」を引けるようにする。後ろ向きの生存変数解析も同じ CFG を使う。例えば `x = f(); x = 2;` で最初の値が後から読まれない場合も、`f()` の呼び出しと副作用の可能性は記録する。

結果には、断定できる事実、到達し得る候補、解析上の `unknown` を区別して持つ。例えば不明な条件で二つの定数に分かれた場合、現段階の値は `unknown` でも、到達定義の集合には両方の代入を残す。解析できない呼び出しは、戻り値や影響を受け得るメンバー・参照先を保守的に扱い、理由とソース位置を返す。

## 7. LWC 等に広げるときの境界

Apex の実装では、Apex JSON から宣言・評価順・呼び出し・例外の情報を取り出す処理と、得られた CFG・読み書きの情報を使ってグラフ上で状態を伝播する処理の境界を明確にする。ソース位置、宣言と参照の ID、CFG の辺、到達定義や `unknown` の理由は、次の言語でも使えるかを確認する対象とする。まず Apex の例で動作と必要な精度を確かめる。

LWC では既存の JS/TS walker を入口の候補にし、モジュール、クロージャー、非同期処理、テンプレートやイベントの結び付きに応じて言語側の情報を組み立てる。両方で共通に使えると分かったグラフ探索や状態伝播から共通化する。 [既存の LWC walker](../../Lwc/walker.ts) · [既存の LWC 解析](../../Lwc/analysis.ts)
