### 2.1 作り方の共通の方針

- **XML のメタデータは、オブジェクトと同じ方式**（中間表現を作らず、`parseXml` の木から `makeXmlJson` で直接 JSON を作る。`types/commons/xmlJson.ts`・`spanJson.ts`）。値は要素名をプロパティ名にし、ファイルにないものは持たない。
- **1 単位 = 1 解析結果 = 1 保存ファイル**（接頭辞で種類を分ける）。Diff は単位の id で対応付ける（`makeIdUnitDiffs`）。子は名前で対応付ける（D）。
- worker の `WorkerTaskType` と `SaveDataType` に種類を足し、`BatchWorker` を継承した worker を作る（`LwcWorker` と同じ）。
- 種類をまたぐ参照（権限 → オブジェクト・項目・Apex、Flow → 項目・Apex・LWC、FlexiPage → LWC）は、保存する JSON には入れず、解析（`processor/<種類>/analysis.ts`）で突き合わせる（LWC の `analyzeLwcBundles` と同じ。ほかの単位の変更で結果が変わるため）。

### 2.2 種類ごとの注意

- **Flow**: 要素は名前（`name`）で対応付ける（D）。接続（`connector.targetReference`）は要素どうしの辺として持ち、Diff では辺の集合（B）で比べる。並び順に意味はない（XML の順はツールが決める）。起動条件・数式（`formulas`）・条件（`conditions`）は、項目の参照（`$Record.Amount__c` など）を取り出す。
- **PermissionSet / Profile**: 権限の行（`objectPermissions` / `fieldPermissions` / `classAccesses` など）は対象の名前で対応付ける（D）。同じ型で 2 つを扱い、Profile にしかないもの（レイアウトの割り当て・ログイン制限）を足す。Profile は数万行になることがあるので、読む要素を表で決め、ほかは無視する。
- **権限の計算**: 「ある項目を編集できるのは誰か」は、Profile・PermissionSet・PermissionSetGroup（ミュートを含む）を合わせた解析にする。
- **CustomLabels**: 1 つのファイルに全ラベルが入るので、単位はラベルごとにするか、ファイル 1 つにしてラベルを子（D）にするかを決める（10 章）。

## 4. 進め方（案）

優先度 A は実装済み（[metadata-a-plan.md](./metadata-a-plan.md)。残りは同 10 章）。2 章の表の A の行は、実装の前に書いた案のまま残している（単位は 1 章の表のとおり）。

1. **権限**（PermissionSet → Profile → PermissionSetGroup）: 同じ型で作れて、オブジェクト・項目・Apex との突き合わせ（「誰が何をできるか」）がすぐにレポートになる。
2. **Flow**: 自動化の変更はレビューで重要。項目・Apex・LWC への参照を取り出す。
3. **画面**（Layout → FlexiPage → CustomTab / CustomApplication）: 項目・LWC がどこに出ているか。
4. **CustomLabels・カスタムメタデータのレコード・CustomPermission・GlobalValueSet**: 小さく、ほかの種類からの参照をつなぐ。
5. **数式の解析**: 項目の影響範囲（オブジェクト・Flow・入力規則）を完成させる。
6. 残り（Aura・Visualforce・共有ルール・C の種類）。
