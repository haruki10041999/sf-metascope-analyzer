# 保存の仕組みの見直し（部分更新）

解析の結果の保存の仕方を調べ、部分的に更新できる形の案をまとめる（2026-11-10）。

- きっかけ: これから JSON の形を何度も変え（[json-redesign-plan.md](./json-redesign-plan.md)）、参照・呼び出しなどの派生の情報も増やす。今の仕組みのままだと、そのたびにすべてを作り直すことになる。
- この文書は調査と案だけ。コードはまだ変えていない。
- 計測は [docs/examples/repository](./examples/repository/) で行った（1.7）。計測のスクリプトはリポジトリの外に置いた。
- 確かめていないことは「未確認」と書く。

## 1. 今の保存の仕組み

### 1.1 何を保存するか

| 項目     | 内容                                                                                                                                                                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 単位     | 単位 1 つ（Apex のクラス 1 つ、LWC のバンドル 1 つ、オブジェクト 1 つなど）を 1 ファイルにする。ファイル単位ではない                                                                                                                               |
| 中身     | 単位の解析結果（`UnitParseResult` = [IdParseResult](../src/analyzer/processor/commons/diff/unit.ts)）をそのまま保存する。`filePath`・`dataType`・`resolvedError`・`result`（`id`・`base` = JSON・`sourceObject`）                                  |
| 入れ物   | `{ formatVersion, data }` を msgpackr（`useRecords: true`）で包む（[commons.ts](../src/analyzer/parser/commons.ts) の `makeMsgPackSaveData`）                                                                                                      |
| 入れない | ソースのファイルそのもの、ファイルの hash、依存関係（定義・参照）、グラフ、差分。`sourceObject` にはソースの一部（各ノードの `context`）が入る                                                                                                     |
| 注意     | `filePath` は絶対パスのまま保存する（[repository.ts](../src/analyzer/unit/repository.ts) の `parseUnitFromTree` が木のルートを付ける）。読み込み側は `locationOf` で `root` からの相対に戻すので、リポジトリを動かすと場所がずれる（影響は未確認） |

### 1.2 置き場所と名前

- 保存先は `<savingRoot>/units/` の 1 フォルダ（[processor.ts](../src/analyzer/unit/processor.ts) の `RepositoryProcessor.create`）。MCP では `SF_METASCOPE_BASE_DIR`（[server.ts](../src/mcp/server.ts)）。
- ファイル名は `<接頭辞><名前>.msgpack`（`class_AccountService`・`lwc_accountList`・`object_Invoice__c` など）。接頭辞は単位の種類ごと（[unitType.ts](../src/analyzer/unit/unitType.ts) の `prefix`・`findUnitTypeBySaveId`）。
- 確認用の JSON（`makeJsonSaveData`）もあるが、本番では使わない。

### 1.3 版の確かめ

- 版は全体で 1 つ（`SAVE_FORMAT_VERSION = 7`。[commons.ts](../src/analyzer/parser/commons.ts)）。JSON の形・キーの作り方・保存名のどれを変えても上げる。
- 読むときに版が違えば `SavedDataVersionError`。`Repository.loadSaved` は、1 つでも版が違えば保存データ全体を「なし」（空のリポジトリ）にする（一部だけ読むと、残りが「追加」に見えるため）。
- `hasSaved`（`hasCurrentSavedData`）は、名前の順で最初の 1 ファイルの版だけを見る。

### 1.4 いつ保存し、いつ読むか

| 処理                                            | 何をするか                                                                                                                                                                             |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RepositoryProcessor.create` → `reset()`        | before = 保存データをすべて読む（`Repository.loadSaved`）。after = 作業ツリーのすべての単位を parse する（`Repository.load`）。差分のキャッシュを捨てる                                |
| `save()`                                        | 保存先を消して（`fs.rm`）、after のすべての単位を書き、`reset()` でもう一度すべて parse する                                                                                           |
| MCP の起動（[server.ts](../src/mcp/server.ts)） | `create` のあと、保存データがなければ `save()`。初回は作業ツリーを 2 回 parse する                                                                                                     |
| MCP の `save_objects`                           | `save()`                                                                                                                                                                               |
| MCP のレポート（`reload: true`）                | `reset()`（[reportTools.ts](../src/mcp/reportTools.ts)）                                                                                                                               |
| MCP の依存関係のツール                          | `get_dependents` など 5 つは、呼ぶたびに作業ツリーをすべて parse してグラフを作る（[dependencyTools.ts](../src/mcp/dependencyTools.ts) の `loadGraph`。processor の after を使わない） |
| worker                                          | `UnitWorker.parseAndSaveAll` は単位ごとに parse と保存をする。`loadAll` は `Repository.loadSaved`（[unitWorker.ts](../src/analyzer/worker/unitWorker.ts)）                             |

- 変わった単位だけを parse し直す `Repository.update`（git の変更ファイル → `changedUnits`）はある。ただし使っているのはテスト（[repository-git.test.ts](../test/unit/repository-git.test.ts)）だけで、`reset()` は使わない。
- git の木（`GitTree`）は `git cat-file --batch` で中身を読む（[sourceTree.ts](../src/analyzer/unit/sourceTree.ts)）。blob の id は取っていない。

### 1.5 メモリに持つもの

| もの             | どこで                                                                                                                   | 使い回しの単位                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| 依存関係のグラフ | [dependencies.ts](../src/analyzer/unit/dependencies.ts) の `dependencyGraphOf`（`WeakMap<Repository, DependencyGraph>`） | `Repository` ごと。値を伏せたリポジトリは `shareDependencyGraph` で元のグラフを使う |
| スナップショット | [snapshot.ts](../src/analyzer/report/snapshot.ts) の `snapshotOf`（`WeakMap`）                                           | `Repository` ごと                                                                   |
| 差分             | `RepositoryProcessor.diffs`                                                                                              | `reset()` まで                                                                      |
| ファイルの一覧   | `WorkingTree.files`・`ProjectTree.files`                                                                                 | 木のオブジェクトごと                                                                |

- `reset()` は新しい `Repository` を作るので、グラフ・スナップショットは丸ごと作り直しになる（単位ごとの使い回しはない）。

### 1.6 毎回作り直すもの

- 単位ごとの定義・参照（`getUnitDependencies`。[units.ts](../src/analyzer/processor/dependency/units.ts)）。保存しない。
- グラフ（`buildDependencyGraph`。[graph.ts](../src/analyzer/processor/dependency/graph.ts)）。参照先の名前を、すべての単位の定義と突き合わせて決める（ない参照の指摘も、定義のある種類の一覧で決まる）ので、ほかの単位の変更で結果が変わる。
- 差分（`diffRepositories`）。すべての単位を比べる（中身が同じ単位も比べる）。
- after 側の parse（作業ツリーのすべての単位）。

## 3. 部分更新の案

### 3.1 版を分ける

| 案                     | 内容                                                                    | 良い点                                                                                     | 悪い点                                                                         | 手間 |
| ---------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ | ---- |
| A. 全体で 1 つ（今）   | `SAVE_FORMAT_VERSION`                                                   | 単純                                                                                       | 問題 1                                                                         | —    |
| B. parser の系統ごと   | Apex・LWC・オブジェクト・翻訳・フォルダ単位の 5 つ（＋入れ物の版 1 つ） | [json-redesign-plan.md](./json-redesign-plan.md) の段階（A・M・LWC）と対応する。数が少ない | フォルダ単位の 1 種類だけ変えても、フォルダ単位すべて（50 種類ほど）を作り直す | 小   |
| C. 単位の種類ごと      | `UnitType` に `formatVersion` を持たせる（約 60）                       | 作り直しがいちばん少ない                                                                   | 共通の部品（値の木・キーの作り方）を変えたときに、上げ忘れが起きやすい         | 中   |
| D. B ＋ 種類ごとの追加 | 系統の版と、種類ごとの版（既定 0）の組                                  | 普段は B、1 種類だけ変えるときは C                                                         | 版が 2 段になる                                                                | 小   |

- どの案でも、入れ物・置き場所・名前の付け方の版（レイアウトの版）は全体で 1 つ残す。

### 3.2 単位ごとの目録（ファイルと hash）

単位ごとに「どのファイルの、どの中身から、どの版の parser で作ったか」を持つ。

```ts
/** 保存した時点の単位 1 つ */
type ManifestUnit = {
    type: string; // 単位の種類
    location: string; // 単位の場所 (リポジトリからの相対パス)
    files: { path: string; hash: string }[]; // filesOf のファイルと中身の hash (名前の順)
    key: string; // hash(type, location, files)。parse の結果の名前に使う
};
type Manifest = { layoutVersion: number; units: ManifestUnit[] };
```

| 論点             | 案                                                                                                                        | メモ                                                                                                                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| hash の種類      | (a) LF にそろえた中身の sha256（今の `hash` と同じ作り方）<br>(b) git の blob の id                                       | (a) は作業ツリー・git のどちらでも同じ値になる（parser が見る中身と同じ）。(b) は git の木なら `ls-tree` で読まずに取れるが、作業ツリーでは改行の変換（autocrlf）で値が変わりうる（未確認） |
| ファイルの一覧   | 単位のファイルの一覧も key に入れる                                                                                       | LWC のバンドルにファイルを足すと、ほかのファイルが同じでも単位は変わる                                                                                                                      |
| 変わったかの判定 | (a) 毎回すべてのファイルを読んで hash<br>(b) 大きさ・更新時刻で先に絞る<br>(c) git の変更ファイル（`changedUnits`）で絞る | (a) は読むだけなので parse より十分速い（116 KB を読む時間は計測していないが、parse の 315 ms より小さいはず。未確認）。(b)(c) は (a) が遅いと分かってから                                  |
| parse の前提     | 単位の parse は、その単位のファイルだけで決まる                                                                           | `UnitType.parseUnit(location, files)` の形がそうなっている。ほかの単位を読んでいる種類がないかは未確認（オブジェクトの分割されたファイルの組み立ては、同じ単位の中）                        |

### 3.3 ソースも保存する

before を「前回の時点のソース」から作り直せるようにする。

| 案                          | 良い点                                                                                                         | 悪い点                                                                                                         |
| --------------------------- | -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| A. 保存しない（今）         | 小さい                                                                                                         | 版を上げると before が消える（問題 2）                                                                         |
| B. hash ごとにソースを保存  | 版を上げても before を parse し直せる。同じ中身は 1 つだけ持つ。サンプルではソース 116 KB（保存データの 14 %） | 保存データが少し増える。ソースに書いた機密の値も保存される（`sourceObject` の `context` にもすでに入っている） |
| C. git の blob から読み直す | 保存が増えない                                                                                                 | 作業ツリーの未コミットの変更を保存した場合は、git に blob がない。git のない使い方で使えない                   |

### 3.4 派生の情報（定義・参照）を単位ごとに保存する

- 定義・参照（`UnitDependencies`）は、その単位の解析結果だけで決まる（`getUnitDependencies(type, result)` の形）。単位ごとに保存してよい（[analysis-plan.md](./analysis-plan.md) 3.2 にも同じ方針がある）。
- 派生の版（`DERIVED_VERSION`）を JSON の版と分ける。参照の種類を足したとき（walker の追加・[json-redesign-plan.md](./json-redesign-plan.md) の A3・M1〜M3）は、派生の版だけを上げる。parse はやり直さず、保存した JSON から定義・参照を作り直す。
- 大きさ: サンプルで JSON の約 45 %（141 KB / 307 KB）。
- 速さ: 作り直しても 1.7 で 8〜30 ms。今の大きさなら保存しなくても困らない。保存する理由は、大きいリポジトリでの時間（比例の仮定で 1 万単位 1〜4 秒）と、MCP の起動の速さ。

| 案                                        | 良い点                             | 悪い点                               | 手間 |
| ----------------------------------------- | ---------------------------------- | ------------------------------------ | ---- |
| A. 保存しない、メモリで単位ごとに使い回す | 保存の形が増えない                 | 起動のたびに作る                     | 小   |
| B. 単位ごとに保存（JSON と別のファイル）  | 派生の版だけ上げられる。起動が速い | 保存のファイルが倍になる             | 中   |
| C. JSON と同じファイルに入れる            | ファイルが増えない                 | 派生の版を上げると JSON ごと書き直す | 中   |

### 3.5 グラフの更新

| 案                                    | 内容                                                                                   | 良い点                               | 悪い点                                                                                                                                   |
| ------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| A. 単位ごとの定義・参照から全体を組む | 変わった単位の定義・参照だけ作り直し、`buildDependencyGraph` は全体で呼ぶ              | 今のコードのまま。正しさを保ちやすい | 単位が多いと組み立てに時間がかかる（1.7 で 4〜8 ms。比例の仮定で 1 万単位 1 秒）                                                         |
| B. グラフを差分で直す                 | 単位のノード・辺を消して足す。名前の突き合わせ・ない参照の指摘を、影響する参照だけ直す | 大きいリポジトリで速い               | 参照先の決まり方が全体の定義に依る（ほかの単位の定義が増えると、別の単位の参照が「ない」から「ある」に変わる）。逆引きの索引が要り、複雑 |
| C. グラフを保存する                   | グラフそのものを保存する                                                               | 起動が速い                           | ほかの単位の変更で変わるので、結局作り直す（[analysis-plan.md](./analysis-plan.md) 3.2 で「保存しない」と決めた）                        |

### 3.6 保存先の形

| 案                                   | 良い点                                                     | 悪い点                                                                                                                           |
| ------------------------------------ | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| A. 単位ごとの msgpack ファイル（今） | 依存を増やさない。1 単位だけ読み書きできる。中身を見やすい | ファイルが多くなる（1 万単位で 2〜3 万ファイル）。何ファイルもまとめて書くとき、途中で止まると壊れる（目録を最後に書けば防げる） |
| B. 1 ファイルにまとめる              | ファイルが少ない                                           | 1 単位だけ書き直せない（部分更新に向かない）                                                                                     |
| C. SQLite（`node:sqlite`）           | まとめて書いても壊れない（トランザクション）。1 ファイル   | Node 22 では実験的な機能（フラグが要る版がある。`engines` は `>=22`）。どの版から使えるかは未確認。中身を見る道具が要る          |
| D. LMDB など                         | 速い                                                       | ネイティブの依存が増える（`package.json` にない）                                                                                |

- 今の依存（`package.json`）でキーと値の保存に使えるのは msgpackr だけ。

### 3.7 キャッシュの捨て方

- 解析結果（`UnitParseResult`）のオブジェクトは、`Repository.update` で変わらなかった単位はそのまま次の `Repository` に渡る。そこで、定義・参照のキャッシュを `WeakMap<UnitParseResult, UnitDependencies>` にすれば、変わった単位だけ作り直せる（捨てる処理を書かなくてよい）。
- グラフ（`dependencyGraphOf`）・スナップショット（`snapshotOf`）は今のまま `Repository` ごとでよい。スナップショットは 0.1 ms。グラフは単位ごとの定義・参照を集めて組むだけになる。
- 差分（`diffRepositories`）は、目録の `key` が同じ単位（同じファイル・同じ中身）を比べずに「変わらない」にできる。`key` の比べ方は版も含める（版が違えば before を作り直したあとに比べる）。

### 3.8 before と after と部分更新

- before は「最後に保存した時点」のまま。保存のときに目録（3.2）を書き換えることで、before を進める。
- 保存した解析結果は、before だけでなく after の parse の使い回しにも使う（同じ `key` なら parse しない）。before と after で同じ単位なら、同じ解析結果のオブジェクトを共有できる。
- 版を上げたときの before: ソース（3.3 B）から、版の古い単位だけを parse し直す。after も同じ `key` なので、作り直した結果を共有する。
- 保存: after の目録を書き、まだない解析結果・ソースを書き足す。parse し直す必要はない（今の `save()` の `reset()` はいらなくなる）。

## 4. 推奨案と段階

### 4.1 推奨の形

ソースと解析結果を中身の hash で引ける「置き場」にし、before はその上の目録 1 つにする。

```text
<savingRoot>/store/
  manifest.msgpack                 before の目録 (レイアウトの版・単位の一覧・各単位のファイルと hash・key)
  sources/<hash>.msgpack           ソース (LF にそろえた中身)。同じ中身は 1 つ
  parsed/<種類>/<key>.msgpack       解析結果 { formatVersion, data }。data は今の UnitParseResult (filePath は相対パス)
  derived/<種類>/<key>.msgpack      定義・参照 { derivedVersion, formatVersion, data: UnitDependencies }
```

| 項目         | 推奨                                                                                                                                                                                            |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 版           | 3.1 D（系統の版 ＋ 種類ごとの追加の版）。入れ物・置き場所の版（レイアウトの版）は全体で 1 つ                                                                                                    |
| 単位の正しさ | 3.2 の目録。hash は LF にそろえた中身の sha256。毎回すべてのファイルを読んで hash を取る（速さが足りなければ、あとで大きさ・更新時刻で絞る）                                                    |
| ソース       | 3.3 B（hash ごとに保存）                                                                                                                                                                        |
| 派生の情報   | まずはメモリで単位ごとに使い回す（3.4 A）。大きいリポジトリで起動が遅いと分かったら保存（3.4 B）。どちらでも派生の版を JSON の版と分ける                                                        |
| グラフ       | 3.5 A（単位ごとの定義・参照から全体を組む）。差分での更新はしない                                                                                                                               |
| 保存先       | 3.6 A（ファイル）。目録を一時ファイルに書いて名前を変える（最後に置き換えるので、途中で止まっても前の before が残る）。目録にない解析結果は保存のあとに消す                                     |
| 読み込み     | before: 目録を読み、各単位の解析結果を `key` で読む。版が古ければソースから parse し直して書き足す。after: 作業ツリーのファイルを hash し、同じ `key` があれば読む、なければ parse して書き足す |

- 保存データが「捨ててもよいキャッシュ」と「before の目録」に分かれる。解析結果・定義・参照は、消えても作り直せる。消えると困るのは目録とソースだけ。
- 古い保存データ（今の `units/`・版 7）は、移行せずに捨てる。今と同じく、最初の 1 回は before なしになる。

### 4.2 段階

| 段階 | 内容                                                                                                                                                                                                                                                                               | 保存の形                  | 効果                                                      |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- | --------------------------------------------------------- |
| S0   | 保存の形を変えずに直せるもの。MCP の依存関係のツールを processor の after（`dependencyGraphOf`）で動かす。`save()` のあとの `reset()` をやめ、before を after にする。定義・参照を `WeakMap<UnitParseResult, …>` で使い回す。計測のスクリプトを `test/` か `docs/examples/` に置く | 変えない                  | 問題 4（一部）・5・7。起動の 2 回の parse がなくなる      |
| S1   | 版を分ける（3.1 D）。`SAVE_FORMAT_VERSION` をレイアウトの版にし、系統の版を `UnitType` から引く。読み込みは、版の違う種類だけ「なし」にする（ほかの種類は読む）。`filePath` を相対パスで保存する                                                                                   | 変える（版を 1 回上げる） | 問題 1・10。JSON の改修で、ほかの系統の before が消えない |
| S2   | 目録とソースの置き場（4.1）。保存は目録を最後に置き換える。before の版が古い単位は、ソースから parse し直す                                                                                                                                                                        | 変える                    | 問題 2・3・9。版を上げても before が残る                  |
| S3   | after の parse を `key` で使い回す（`reset()` は変わった単位だけ parse する）。差分は `key` の違う単位だけ比べる                                                                                                                                                                   | 変えない（S2 の上）       | 問題 4・8                                                 |
| S4   | 派生の版を分ける。必要なら定義・参照を単位ごとに保存する（3.4 B）                                                                                                                                                                                                                  | 足す                      | 問題 6。参照の種類を足しても parse をやり直さない         |
| S5   | 必要なら: 大きさ・更新時刻で hash を省く、git の変更ファイルで絞る、ファイルの監視                                                                                                                                                                                                 | 変えない                  | 大きいリポジトリでさらに速く                              |

- S1 は [json-redesign-plan.md](./json-redesign-plan.md) の A1（最初の版上げ）より先に入れる。そうすれば、Apex の版上げ（A1・A2・A4〜A6）でメタデータ・LWC の before が消えない。
- S2 は A2（Apex の式がすべて変わる）より先に入れるとよい。版を上げても before をソースから作り直せるので、改修の前後で同じ before に対する差分のレポートを比べられる。
- A3・M1・M2（走査・派生の情報。JSON は変えない）は、S4 のあとなら派生の版を上げるだけで済む。S4 の前なら、今のとおり毎回作り直すので版を上げる必要はない（派生の情報を保存していないため）。
- [json-redesign-plan.md](./json-redesign-plan.md) 5 章の「保存の版は 3 つの領域で共通」は、S1 のあとは「系統ごとに上げる」に変える。

### 4.3 テスト

| テスト                         | 内容                                                                                                        |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| 保存と読み込みの往復           | サンプルを保存して読んだ before が、作業ツリーを parse した結果と同じ（今の `repository.test.ts` を広げる） |
| 版の違う系統だけ作り直す       | 系統の版を 1 つ上げたとき、その系統の単位だけ parse し直し、ほかは読み込みで済む（parse の回数を数える）    |
| ソースからの before の作り直し | 版を上げたあとの before が、上げる前に保存したソースを今の parser で parse した結果と同じ                   |
| 変わった単位だけ parse         | 1 ファイルを変えて `reset()` したとき、その単位だけ parse する。ファイルの追加・削除・名前の変更も          |
| 途中で止まった保存             | 目録を書く前に止めたとき、前の before がそのまま読める                                                      |
| グラフ                         | 使い回した定義・参照から組んだグラフが、すべて作り直したものと同じ                                          |
| 差分                           | `key` で比べるのを省いた差分が、すべて比べた差分と同じ（サンプルの before / after）                         |
