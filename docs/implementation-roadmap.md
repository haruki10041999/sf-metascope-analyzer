# 実装のロードマップ（レポート・カタログ・MCP・データベース）

解析（JSON・Diff・依存関係・data provider）はおおむねそろった（[json-redesign-plan.md](./json-redesign-plan.md)・[save-format-plan.md](./save-format-plan.md)）。次は、それを使う側を作る。

1. **レポート**: JSON で書いたレポート仕様から HTML を作る仕組み。
2. **コンポーネントとカタログ**: 見た目のそろった表示部品と、LLM が読んで仕様を書けるカタログ。
3. **MCP 連携**: 初期処理・ツール・プロンプト。
4. **データベース**: 保存の形を msgpack のファイルから SQL に移す。

この文書は、ライブラリ（今あるものと、ネットで調べた候補）を見直し（2 章）、スキーマのライブラリを 1 つにそろえる方針（3 章）、作り（4 章）、データベース（5 章）、順番（6 章）を決めるためのもの。調べた日は 2026-11-17。R0〜R5・Q0〜Q4 は実装した（8 章）。残りの作業は [todo.md](./todo.md) にまとめた。

### 目的と既定（2026-11-17 に決めた）

- **第一の目的はドキュメントの作成とコードの理解**。差分（前回保存した時点・git の範囲）と影響の調査は、その補助。
- **レポートの形はこちらで固定しない**。雛形はいくつか用意して使えるようにする（ドキュメントの `system_overview`・`permission_overview` を主に、差分の `release_review`・`impact_analysis` を補助に）。そのうえで、AI に組ませるか、利用者が自分で書くかは利用者に任せる。利用者がレポートをカスタマイズできることが、このリポジトリの強み。
- **既定は今の状態のすべて**: provider・MCP のツールの既定は 1 時点（作業ツリー）のすべてを返し、行に `status` を付けない。差分は `diff: true`（保存した基準 → 作業ツリー）か `compare`（git の範囲）を、ツールか文書に書いたときだけ。`onlyChanged` は比べたときだけ効く。差分だけを返す provider は `requiresComparison`（比べる時点がなければ問題にする）。
- 優先度を決めるときは、ドキュメント・理解に効くもの（オブジェクトの詳細・ER 図・クラスの概要・コンポーネントの一覧・画面のワイヤーフレームなど）を、差分・チェックのもの（`*.diffs`・`change.*`・findings）より先にする。
- 決めたことの詳細: [report-components-plan.md](./report-components-plan.md) 5 章、[apex-json-analysis.md](./apex-json-analysis.md) 7 章、[lwc-snapshot-plan.md](./lwc-snapshot-plan.md) 7 章、[todo.md](./todo.md) 9 章。

## 3. スキーマのライブラリを zod にそろえる

| 観点        | zod                                                                                                                    | typia                                                                                                                   |
| ----------- | ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| MCP の SDK  | v1 は zod を受け取る。v2 は Standard Schema（検証と JSON Schema の出力の両方）を受け取り、zod 4.2 以降はその両方を持つ | v1 では使えない。v2 で使うには JSON Schema の出力（Standard JSON Schema）が要るが、typia が持つことは確かめられなかった |
| json-render | カタログは zod                                                                                                         | 使えない                                                                                                                |
| JSON Schema | `z.toJSONSchema`（手元で確かめた）                                                                                     | `typia.json.schemas<[...]>()`（型のコメントが説明になる。手元で確かめた）                                               |
| 書き方      | スキーマを書き、型は `z.infer` で作る                                                                                  | 型を書き、コンパイル時の変換で判定・スキーマを作る（`ttsc` の変換が要る）                                               |
| 今の使い方  | MCP のツールの引数                                                                                                     | `createIs` を 71 個定義。使っているのは 2 つ                                                                            |

- **zod にそろえる**。MCP と json-render という外との境目が zod を求めるため。typia は、判定の 2 か所を `kind` の判定に置き換え、71 個の定義を消せばやめられる（JSON のノードはどれも `kind` を持つので、判定は `node.kind === 'fxBinary'` などで足りる）。
- provider の出力の型（`types.ts`）は、zod のスキーマに書き直し、型は `z.infer` で作る。カタログの JSON Schema はそこから作る（typia のように型のコメントから説明を作れないので、説明は `.describe()` で書く）。
- 解析の JSON の型（`types/apex`・`types/lwc`・`types/metadata`）は、今のまま TypeScript の型にしておく（数百あり、外との境目ではないため）。データベースから読んだ木を検証したくなったら、その時にスキーマを考える。
- typia をやめると、`ttsc` の変換が要らなくなる。`ttsx`（実行）・`ttsc`（ビルド）を別の道具（`tsx`、Node の型を消す実行など）に替えられるかは、R0 で確かめる。

## 4. レポート・カタログ・MCP の作り

[report-components-plan.md](./report-components-plan.md) の 1 章の形（skill がレポート仕様を書き、AI は文章とデータの選択だけをし、数値・一覧・図は解析の結果をそのまま使う）を実装に落とす。

### 4.1 json-render を使う形（試作で決める）

```text
provider の登録表 (zod: 引数・出力)          コンポーネントのカタログ (json-render の defineCatalog。zod の props)
        │                                              │
        ├── MCP: get_report_data ── AI が材料を読む ─┤── MCP: カタログ (catalog.prompt())
        │                                              ▼
        │                               AI が仕様 (JSON) を書く: elements と、データは { "$state": "/data/<名前>" }
        ▼                                              │
build_report: 仕様の data の宣言から provider を実行 → state に入れる → validateSpec → 事前ビルドの HTML に差し込む
```

- 仕様に「どの provider をどの引数で使うか」を書く場所（`data: { flowInterface: { provider: 'flow.interface', args: {...} } }`）を足し、ビルドがそれを実行して `state` に入れる。AI はデータを書かず、`$state` で参照するだけにする。
- 試作で確かめること: 仕様の形が足りるか（セクション・注記・ソースの位置への結び付け）、`validateSpec` が props を zod で検証するか、事前ビルドの 1 つの HTML で描けるか、版の変化の速さ。
- 合わなければ、[report-components-plan.md](./report-components-plan.md) 1.1 の自前の仕様（zod）にする。その場合も、カタログ・検証・描画の分け方は json-render と同じにする。

### 4.2 登録表を 1 か所にする

| 登録表         | 中身                                                                         | 使う所                                     |
| -------------- | ---------------------------------------------------------------------------- | ------------------------------------------ |
| provider       | 名前・説明（LLM 向け）・引数（zod）・出力（zod）・実行する関数               | MCP のツール・仕様の検証・カタログ・ビルド |
| コンポーネント | 名前・説明・props（zod）・受け取れるデータの形・例（json-render のカタログ） | カタログ・仕様の検証・描画                 |

- 手で書いた一覧を別に持たない。カタログ・JSON Schema・MCP のツールの説明はすべて登録表から作る。
- カタログは `npm run catalog` で `docs/catalog/` にも書き出し、テストで「登録表と一致する」ことを確かめる。

### 4.3 コンポーネントと見た目

| 種類     | 例                                                                                                                  | 作り方                                                                                     |
| -------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 汎用     | `Section`・`Narrative`（Markdown）・`Callout`・`SummaryCards`・`DataTable`・`Badge`（status の色）・`SourceSnippet` | shadcn/ui の部品を包む。status（added / removed / changed）の色・アイコンは 1 か所で決める |
| 図       | `Graph`（依存関係・Flow・ER）                                                                                       | `@xyflow/react` ＋ 自動配置                                                                |
| 種類ごと | `FlowInterfaceTable`・`PermissionDiffTable` など（[report-components-plan.md](./report-components-plan.md) 2 章）   | 汎用の部品を組み合わせる。個別の見た目を作らない                                           |

- テーマ（色・文字・余白）は Tailwind v4 の CSS 変数で 1 か所に置く。種類ごとのコンポーネントは汎用の部品だけで作り、色を直接書かない。

### 4.4 HTML の作り方

- viewer は **事前に 1 回だけ** ビルドする（Vite ＋ Tailwind v4 ＋ `vite-plugin-singlefile` で `dist/viewer/report.html`）。HTML の中に `<script type="application/json" id="report">` の置き場を作っておく。
- レポートを作るときは、仕様を検証して provider を実行し、仕様とデータをその置き場に入れて書き出すだけにする。実行時に Vite を使わない（1 章のビルドの問題と、データが入らない不具合の両方がなくなる）。
- データの JSON は `</script>` を壊さないように `<` をエスケープする。機密の値は今の `runReportProvider` と同じく伏せる（`report/mask.ts`）。
- 同じ HTML を MCP Apps の `ui://` のリソースとしても出す（4.5）。
- JavaScript なしの HTML（印刷・メール）が要るなら、React の `prerender` で静的な HTML を作る道を足す。

## 5. データベース

### 5.1 SQLite か PostgreSQL か

| 観点             | SQLite                                                                                | PostgreSQL                                                           |
| ---------------- | ------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 使われ方との相性 | 1 人・1 つのリポジトリ・ローカルの MCP（今の使い方）。ファイル 1 つで、準備が要らない | 複数の人・複数のリポジトリで、解析の結果を共有するサーバー           |
| 配布             | `node:sqlite` なら依存が増えない                                                      | サーバーの用意が要る（PGlite なら要らないが、アルファ・接続は 1 つ） |
| JSON             | JSON の関数・JSONB（3.45 以降）                                                       | JSONB と索引（GIN）が強い                                            |
| 木の問い合わせ   | 再帰の `WITH` がある                                                                  | 同じ                                                                 |
| 同時に書く       | 1 つずつ（WAL なら読みは並ぶ）                                                        | 強い                                                                 |

- **最終のゴールも SQLite** にする。このツールの中心は、ローカルのリポジトリを解析して MCP で答えることで、サーバーを前提にしない。
- ただし、PostgreSQL に移せる書き方にしておく: SQL は両方で通る形にする（`STRICT` の表・`json` の関数の違いは保存の層に閉じ込める）、保存の層を 1 つのインターフェースにする。チームで解析の結果を共有する「サーバーの形」が要るようになったら、そのとき PostgreSQL を足す。

### 5.2 ノードの単位: JsonType と StructureJsonType を 1 行に

提案のとおり、JsonType（`kind` と `sourceKeys` を持つもの）と StructureJsonType（`sourceKeys` が `{ base, name }`）を 1 行にする。Apex・LWC・メタデータのどの種類も同じ表にそろう。

**試作で確かめたこと**（サンプルの after・83 単位、`node:sqlite`、手元の Windows 11・Node 26.8、1 回だけ測った値）:

| 項目                                           | ノードの行（案 A）                                  | 単位の木を 1 行（案 B、JSONB）         |
| ---------------------------------------------- | --------------------------------------------------- | -------------------------------------- |
| 行                                             | ノード 3,285（うち StructureJsonType 141）・単位 83 | 単位 83                                |
| 元の JSON と一致するか（組み立て直して比べた） | **全 83 単位で一致**                                | 全 83 単位で一致                       |
| 書く時間                                       | 55 ms                                               | 16 ms                                  |
| 全単位を読む時間                               | 45 ms（組み立て直しを含む）                         | 10 ms                                  |
| ファイルの大きさ                               | 776 KB（索引 3 つを含む）                           | 536 KB                                 |
| `kind` ごとの数を数える問い合わせ              | 3.6 ms（SQL でそのまま）                            | できない（中を引く JSON の関数が要る） |

- 組み立て直しは案 B の約 4.5 倍かかるが、絶対値は小さい（比例の仮定で 1 万単位で約 5 秒）。しかも案 A は、要る単位・要る種類だけを読める（provider が使うのはいくつかの種類だけ）ので、全単位を読むことは少ない。
- **案 A を推す**（前の版の推奨の案 B から変えた）。表が 1 種類にそろい、SQL でノードを直接引け、索引の表を別に持つ必要がない。

ノードの行の作り方（試作で使ったもの）:

- 子のノードは、親の中身（`content`）のその場所を `{"$node": <nodeId>}` に置き換える。子の行には親の `nodeId` と、親の中の場所（`$.conditionBlock[0].block[1]` のようなパス）を持つ。並び順はパスで決まる。
- `kind` を持たない入れ物（if の分岐など。サンプルで 1,082）は親の `content` の中に残す。
- 単位の根（`ApexUnitJson` などはノードではない）は単位の行の `root` に、同じ置き換えをして持つ。
- `objectKey` は中身の hash なので重なる（同じ単位で 855 件）。主キーは連番の `nodeId` にする。
- StructureJsonType は `sourceKeys`（`base`・`name` など）をそのまま 1 列に持つ。主な位置（`base`）は別の列にも持って引けるようにする。

### 5.3 テーブルの案

```sql
CREATE TABLE source (hash TEXT PRIMARY KEY, text TEXT NOT NULL);          -- LF にそろえたソース (同じ中身は 1 つ)
CREATE TABLE unit (
    unit_id INTEGER PRIMARY KEY,
    key TEXT NOT NULL UNIQUE,              -- 種類・場所・ファイルと hash の hash (今の store の key)
    type TEXT NOT NULL, location TEXT NOT NULL, id TEXT NOT NULL,
    format_version TEXT NOT NULL,
    data_type TEXT NOT NULL,               -- apexUnit・lwcBundle・error など
    root TEXT NOT NULL,                    -- 単位の根 (ノードは {"$node": id})
    resolved_error TEXT NOT NULL           -- 指摘 (JSON)
);
CREATE TABLE unit_file (unit_id INTEGER NOT NULL REFERENCES unit, path TEXT NOT NULL,
    hash TEXT NOT NULL REFERENCES source, PRIMARY KEY (unit_id, path));
CREATE TABLE node (
    node_id INTEGER PRIMARY KEY,
    unit_id INTEGER NOT NULL REFERENCES unit,
    parent_id INTEGER REFERENCES node,     -- 根の直下は NULL
    path TEXT NOT NULL,                    -- 親の content (根の直下は unit.root) の中の場所
    kind TEXT NOT NULL,
    object_key TEXT NOT NULL,              -- StructureJsonType は base の
    source_key TEXT NOT NULL,
    structure_keys TEXT,                   -- StructureJsonType の sourceKeys ({ base, name, ... })。ほかは NULL
    content TEXT NOT NULL                  -- kind・sourceKeys を除いた中身 (子のノードは {"$node": id})
);
CREATE INDEX node_unit ON node (unit_id); CREATE INDEX node_kind ON node (kind); CREATE INDEX node_parent ON node (parent_id);
CREATE TABLE span (                        -- sourceObject の位置。context は持たない (source から切り出す)
    unit_id INTEGER NOT NULL REFERENCES unit, source_key TEXT NOT NULL, object_key TEXT NOT NULL,
    file_path TEXT NOT NULL,
    start_offset INTEGER NOT NULL, start_line INTEGER NOT NULL, start_column INTEGER NOT NULL,
    end_offset INTEGER NOT NULL, end_line INTEGER NOT NULL, end_column INTEGER NOT NULL,
    PRIMARY KEY (unit_id, source_key)
);
CREATE TABLE snapshot (name TEXT PRIMARY KEY, created_at TEXT NOT NULL);   -- 'before' (今の目録)
CREATE TABLE snapshot_unit (name TEXT NOT NULL REFERENCES snapshot, unit_id INTEGER NOT NULL REFERENCES unit,
    PRIMARY KEY (name, unit_id));
-- 依存関係 (定義・参照) は、SQL で問い合わせたくなったら決める (今は S4 の派生の版つきで保存すればよい)
```

- `context` は持たない。サンプルの約 3,550 件すべてで、保存したソースを `start.offset`〜`end.offset` で切り出したものと一致した（今の sourceObject の 928 KB のほとんどがなくなる）。
- 保存は 1 つのトランザクションにする（今の「目録を最後に置き換える」が要らなくなる）。
- PostgreSQL に移すときは、`content`・`root` などを `jsonb`、連番を `GENERATED ... AS IDENTITY` にする。

### 5.4 HTML・XML・CSS にも IR を入れるべきか

- **データベースのためには要らない**。表がそろうかを決めるのは、IR ではなく JSON の形（位置を持つものがすべて `kind` と `sourceKeys` を持つノードになっているか）。5.2 の試作は、メタデータ・Visualforce・Aura・LWC のテンプレートと CSS もそのまま同じ表に入った。
- IR（Apex・LWC の `*_IR` のような、parser の木を型付きのノードにする層）の良い点は、ノードの作り方（キー・位置・読めないものの扱い）を 1 つにそろえ、parser の結果の検査をそこに集められること。XML は自前の `types/commons/xml.ts` が位置つきの要素の木を作っており、すでに IR に近い。
- 入れるかは、データベースとは別に「メタデータの JSON の作り方の整理」として決める。データベースのために先にやる必要はない。
- データベースのために先にやるべきなのは、**位置を持つのにノードになっていないもの**を洗い出すこと（値の木の中の要素、`kind` を持たない入れ物で位置を持つものなど）。これは Q0 で数える。

### 5.5 ライブラリ

- `node:sqlite` を使う。`engines` は、実験的の警告がなくなった版（24.15 以降。Node 24 は LTS）に上げる。安定版ではない（リリース候補）ので、使う API を保存の層に閉じ込める。
- ネイティブの依存（`better-sqlite3`）は、`node:sqlite` で困ったときの代わりにする。

### 5.6 SQL の組み立て

- 最初は SQL を手で書き、保存の層（`SqliteUnitStore`）の中に閉じ込める（表が少ないため）。
- PostgreSQL も扱うことになったら、`kysely`（両方に対応した SQL の組み立て）を入れる。`node:sqlite` で使えるか（kysely の SQLite の方言が求める形に合うか）は、そのときに確かめる。
