# Apex の JSON の見直し（調査。LWC の JS / TS の JSON に合わせる）

改修方針のまとめは [json-redesign-plan.md](./json-redesign-plan.md)。この文書は 2026-11-10 の調査の結果。

LWC の JS / TS の JSON は作り直した（[lwc-json-types.md](./lwc-json-types.md) 5〜8 章）。決めたことは次の 4 つ。

- 文・式の `kind` を明示する（形から推定しない）。
- 式はソースの文字列を持たない。すべて構造で表す。
- 文はすべて構造（境界ノード）。Diff の境界は文と `jsMemberAccess` / `jsCall` だけ。
- 呼び出し・イベントなどの派生の情報は JSON に持たず、解析の走査（[walker.ts](../src/analyzer/processor/Lwc/walker.ts)・[calls.ts](../src/analyzer/processor/Lwc/calls.ts)）で出す。

この文書は、Apex の JSON（[types/apex/](../src/analyzer/types/apex/)。IR は [apex_IR](../src/analyzer/types/apex_IR/)）と使う側を、この 4 つを目標として見直す。

- 観点 1: 粒度・形が LWC と同じか（2 章）
- 観点 2: 処理・生成する情報が LWC と同じか（3 章）
- 観点 3: Apex として大事な情報が抜けていないか（4 章）
- 見つけた不具合（5 章）、直し方の案と順番（6 章）、決めること（7 章）

調べ方: コードを読んだ。一部は小さなソースを `parseApexUnitFiles` → JSON・`getApexDependencies`・`makeExpressionDiff` に通して確かめた（「実行で確認」と書く）。確かめていないものは **未確認** と書く。

## 0. まとめ

| #   | 見つけたこと                                                                                                                                                                                                                                                                                                                                                                      | 優先度 |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| 1   | **式の種類が暗黙。** `memberAccess`・`type`・`soql`・`sosl` 以外の式は `kind` を持たない。識別子・`this`・`super`・`void.class` はただの文字列。Diff（[expression.ts](../src/analyzer/processor/Apex/diff/expression.ts#L512-L590)）と GumTree（[getExpressionLabel](../src/analyzer/processor/Apex/diff/gumtree/tree.ts#L26-L47)）と依存関係が、それぞれ形から種類を推定している | 高     |
| 2   | **式にソースの文字列・定数が残る。** リテラルは引用符つきの文字列（`"'abc'"`）、`SubJson.parentheses: '()'`、`NoInitInstanceJson.value: '{}'`、`initType: 'list \|\| set'`、`break` / `continue` の `value`、回復のときの `ctx.getText()`                                                                                                                                         | 高     |
| 3   | **派生の情報を出す走査がない。** 依存関係（[dependency/apex.ts](../src/analyzer/processor/dependency/apex.ts#L562)）・ラベル（[labelAnalysis.ts](../src/analyzer/processor/Metadata/labelAnalysis.ts#L56)）・Invocable（[references.ts](../src/analyzer/processor/Metadata/references.ts#L189-L210)）が、それぞれ JSON を独自にたどる。`dottedName` は 2 か所にある               | 高     |
| 4   | **依存関係の不具合（実行で確認）。** プロパティの getter / setter の本体を見ない、`this.f()` の呼び出しが出ない、`Database.Batchable<T>` のような `.` つきの型が出ない、サブクエリの項目が出ない、`Database.insert(list, false)` が DML にならない                                                                                                                                | 高     |
| 5   | **Diff の不具合（実行で確認）。** `accA.save()` → `accB.save()` の差分に `object` が出ない（メソッド呼び出しを `MethodCallJson` として比べるため）                                                                                                                                                                                                                                | 高     |
| 6   | **SOSL の検索語が曖昧（実行で確認）。** `FIND :term` と `FIND 'term'` がどちらも `find: "term"` になる                                                                                                                                                                                                                                                                            | 高     |
| 7   | 文の形が LWC とずれる。条件を包む境界ノード（`ifCondition` など）、`body` と `block` の混在、`block` が 1 文か配列か、`localVariable` の入れ子、`forCondition` の 2 つの形を `initializeType` の有無で分ける                                                                                                                                                                      | 中     |
| 8   | 修飾子の分類（`lwcAnnotation`・`flowAnnotation` など 11 の入れ物）は派生の情報。アノテーションの引数は引用符つきの文字列                                                                                                                                                                                                                                                          | 中     |
| 9   | Diff は Apex のほうが細かい（文・式の kind ごとの型付きの差分）。LWC の本体は GumTree の結果のまま。ここは LWC が後で Apex に合わせる側                                                                                                                                                                                                                                           | 参考   |
| 10  | [apex-json-analysis.md](./apex-json-analysis.md) 6.1 は古い。文の型付きの Diff はもうある（[statement.ts](../src/analyzer/processor/Apex/diff/statement.ts#L333-L367)）                                                                                                                                                                                                           | 低     |

段階（6.2）: 0. JSON を変えない不具合の修正 → 1. 曖昧さをなくす小さな変更 → 2. 式の kind → 3. 解析の走査と派生の情報 → 4. 文の形 → 5. 宣言・修飾子・入れ物 → 6. 型・SOQL の残り。

## 1. 用語

[lwc-json-types.md](./lwc-json-types.md) 1 章と同じ。

| 呼び方     | 形                               | Apex の今の例                                                                                       |
| ---------- | -------------------------------- | --------------------------------------------------------------------------------------------------- |
| 境界ノード | `kind` と `sourceKeys`           | 文、`memberAccess`、宣言、`type` の最上位、`soql` と SOQL の部品（`selectEntry` など）              |
| 位置だけ   | `sourceKeys` だけ（`kind` なし） | 式（[ExpressionValueKeys](../src/analyzer/types/apex/expression.ts#L228)）、リテラル、`VariantJson` |
| キーなし   | どちらもない                     | 型の中身、`if` の分岐の入れ物、SOQL の `select` / `from` / `where` の入れ物                         |
| 文字列     | 値が `string`                    | 識別子、`this` / `super`、回復のときのソースの文字列                                                |

LWC は段階 2 で「位置だけ」をなくした（式はすべて `kind` を持つ）。Diff の境界は `jsMemberAccess` / `jsCall` と文だけで、ほかの式は `kind` を持つが親の値として比べる。

### 2.4 SOQL / SOSL

LWC に当たるものはない。境界ノード（`soql`・`selectEntry`・`fromField`・`singleCondition`・`groupBy`・`orderField`・各句）は `kind` を持つ。入れ物は `type` で種類を明示しているものが多い。直すのは曖昧なところと文字列だけにする。

名前の案: LWC に合わせて `ApexCallInfo`・`ApexDmlInfo`・`ApexQueryInfo`（SOQL・SOSL・動的 SOQL）・`ApexTriggerContextInfo` などにする。どれも `kind` を持たず `sourceKeys` を持つ。依存関係の `references` は、これらから作る。

- 段階 2 を段階 3 より先にする理由: 走査の部品（`dottedName` など）を kind のある式で一度だけ書けばよい。kind のない式のまま走査を作ると、`getExpressionLabel` の推定を走査にも持ち込む（[apex-json-analysis.md](./apex-json-analysis.md) 2.1 の案がそうなっている）。
- 段階 3 を段階 4 より先にする理由: LWC は走査を最後（段階 6）にしたが、Apex は依存関係が JSON の形に強く依存している（2.5）。先に走査に移すと、段階 4〜6 で直す使う側が walker と Diff だけになる。
- 段階 2 の依存関係は「つなぎの修正」（文字列の判定を kind の判定に置き換えるだけ）。段階 3 で作り直す。
- 派生の情報の名前・形は LWC の `LwcCallInfo` に合わせる（kind なし、`sourceKeys`、`context`）。
