# JSON の改修方針（Apex・メタデータ・LWC の残り）

LWC の JS / TS の JSON を作り直した（[lwc-json-types.md](./lwc-json-types.md)）。同じ観点で Apex とメタデータを見直し、3 つの領域をそろえるための改修方針をまとめる（2026-11-10）。

- 見直しの詳しい結果: Apex は [apex-json-review.md](./apex-json-review.md)、メタデータは [metadata-json-review.md](./metadata-json-review.md)。どちらもコードを読んで確かめ、一部は小さな入力を通して確かめた（各文書の「実行で確認」）。
- 見た観点:
    1. 粒度・形が LWC と同じか。
    2. 処理・生成する情報が LWC となるべく同じか。
    3. その領域として大事な情報が抜けていないか。
- この文書は方針だけ。コードはまだ変えていない。6 章の決めることは、2026-11-10 にすべて案のとおりに決めた。

## 1. 3 つの領域でそろえること（共通の方針）

LWC で決めたこと（[lwc-json-types.md](./lwc-json-types.md) 7 章）を、Apex とメタデータにも当てる。

| #   | 方針                                                                                                                                              | LWC（今）                   | Apex（今）                                                                     | メタデータ（今）                                                                                   |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| 1   | 種類は `kind` で明示する（形から推定しない）                                                                                                      | 済み                        | 式の多くが `kind` なし。Diff・GumTree・依存関係が別々に推定する                | 種類ごとの JSON は `kind` あり。値の木（Flow の要素の中身など）は `kind` なし                      |
| 2   | 式・数式はソースの文字列を持たず、構造で表す                                                                                                      | 済み（型の `text` を除く）  | 識別子は文字列。リテラルは引用符つき。`'()'`・`'{}'` などの定数が残る          | 数式・条件・差し込み（`{!...}`）がすべて文字列                                                     |
| 3   | 文（Flow の要素など、処理の単位）は構造で持ち、境界ノード（`kind` と `sourceKeys`）にする                                                         | 済み                        | 文はあるが、条件を包む `kind`・`body` と `block` の混在など、形が LWC とずれる | 種類ごとに境界ノードの決め方が違う                                                                 |
| 4   | 派生の情報（呼び出し・参照・イベントなど）は JSON に持たず、共通の走査（walker）と解析で出す                                                      | 済み（`references` を除く） | 走査がない。依存関係・ラベル・Invocable がそれぞれ JSON をたどる               | 参照の取り出しが 4 か所以上。Flow だけ `references` を JSON に持つ                                 |
| 5   | 参照の種類の名前（語彙）は 1 つ（[types.ts](../src/analyzer/processor/dependency/types.ts) の `DependencyTargetType`）にする                      | ほぼ同じ                    | ほぼ同じ                                                                       | 語彙が 4 つあり、グラフの `TARGET_ALIASES` であとからつなぐ。同じ参照が 2 本の辺になるところがある |
| 6   | エラーは JSON のノードにしない（`resolvedError` だけ）                                                                                            | 済み                        | 済み                                                                           | 済み                                                                                               |
| 7   | 本体の Diff は GumTree と型ごとの差分。「呼び出しが増えた」のような意味の差分は、2 つの時点の解析の結果を比べて出す（Diff には入れない）          | GumTree                     | 文・式の型ごとの差分（LWC より細かい）                                         | 種類ごとの差分と値の木の差分                                                                       |
| 8   | JSON の形を変えるたびに、ゴールデン（[golden.test.ts](../test/ir/golden.test.ts)）を確かめてから作り直し、`SAVE_FORMAT_VERSION`（今は 7）を上げる | —                           | —                                                                              | —                                                                                                  |

走査（walker）は、LWC の [walker.ts](../src/analyzer/processor/Lwc/walker.ts) と同じ形（`kind` ごとの Visitor、`composeXxxVisitors`、文脈 `functionDepth`・`loopDepth`・`inTry` など）を Apex とメタデータにも作る。派生の情報の型は、LWC の `LwcCallInfo` と同じく `kind` を持たず `sourceKeys` を持つ形にそろえる。

## 2. Apex（詳しくは [apex-json-review.md](./apex-json-review.md)）

### 2.1 主な問題

| #   | 問題                                                                                                                                                                                                                                                                                                                | 優先度 |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| 1   | **不具合（実行で確認）**: 依存関係でプロパティの getter / setter の本体を見ない、`this.f()` の呼び出しが出ない、`Database.Batchable<T>` のような `.` つきの型が出ない、サブクエリの項目が出ない、`Database.insert(list, false)` が DML にならない。Diff で `accA.save()` → `accB.save()` の `object` の変化が出ない | 高     |
| 2   | SOSL の `FIND :term` と `FIND 'term'` が同じ JSON（`find: "term"`）になる                                                                                                                                                                                                                                           | 高     |
| 3   | 式の種類が暗黙（`memberAccess`・`type`・`soql`・`sosl` 以外は `kind` なし）。式にソースの文字列・定数が残る                                                                                                                                                                                                         | 高     |
| 4   | 派生の情報を出す走査がない                                                                                                                                                                                                                                                                                          | 高     |
| 5   | 文の形が LWC とずれる（条件を包む `kind`、`body` と `block`、`localVariable` の入れ子、`for` の 2 つの形）                                                                                                                                                                                                          | 中     |
| 6   | 修飾子の 11 の分類（名前で決まる派生の情報）が JSON にある。アノテーションの引数が引用符つきの文字列                                                                                                                                                                                                                | 中     |
| 7   | JSON にあるが使われていない情報（sharing・アノテーションの引数・SOQL の WITH / FOR UPDATE / HAVING）、派生の情報になっていない情報（トリガーの文脈 `Trigger.new` など、assert、非同期の呼び出し、動的 SOQL、callout）                                                                                               | 中     |

### 2.2 段階

| 段階 | 内容                                                                                                                                      | JSON             | 保存の版 |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------- | -------- |
| A0   | 2.1 の 1 の不具合を直す（依存関係と Diff）                                                                                                | 変わらない       | そのまま |
| A1   | SOSL の `find` を `literal` / `bind` に分ける                                                                                             | SOSL だけ        | 上げる   |
| A2   | 式に `kind` を付け、ソースの文字列・定数をなくす。GumTree の `getExpressionLabel` の推定をなくす                                          | 式がすべて変わる | 上げる   |
| A3   | 解析の走査（`walkApexJson`）と派生の情報（`ApexCallInfo`・`ApexDmlInfo`・`ApexQueryInfo` など）。依存関係・ラベル・Invocable を走査に移す | 変わらない       | そのまま |
| A4   | 文の形を LWC にそろえる                                                                                                                   | 文が変わる       | 上げる   |
| A5   | 修飾子（分類を解析へ）・アノテーションの引数（式の JSON）・入れ物                                                                         | 変わる           | 上げる   |
| A6   | 型の `customType`・SOQL の残り・名前をそろえる                                                                                            | 一部             | 上げる   |

- LWC は走査を最後にしたが、Apex は依存関係が JSON の形に強く頼っているので、A3 を文の作り直し（A4）より先にする。A4〜A6 で直す使う側が walker と Diff だけになる。
- A2 を A3 より先にする。走査の部品（名前の並びなど）を `kind` のある式で一度だけ書けばよい。
- Apex のゴールデン（28 ファイル）は A2・A4・A5 で全部変わる。LWC と同じく、「消したもの・名前を変えたもの」を古いゴールデンに当てて新しいものと同じになるかを、スクリプトで確かめる。

## 3. メタデータ（詳しくは [metadata-json-review.md](./metadata-json-review.md)）

### 3.1 主な問題

| #   | 問題                                                                                                                                                                                                                                                                                                    | 優先度 |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| 1   | 数式・条件・差し込み（`{!...}`）が文字列のまま。数式は依存関係を作るときだけ字句に分ける（[formula.ts](../src/analyzer/processor/dependency/formula.ts)）                                                                                                                                               | 高     |
| 2   | 参照の取り出しが 4 か所以上（Flow の parse、[referenceAnalysis.ts](../src/analyzer/processor/Metadata/referenceAnalysis.ts)、[units.ts](../src/analyzer/processor/dependency/units.ts)、種類ごとの解析）。語彙が 4 つ。同じ参照が 2 本の辺になるところ（権限の `pageAccesses`、Flow の `{!$Record.X}`） | 高     |
| 3   | どこにも出ずに消える情報: 依存する選択リストの `valueSettings`、FlexiPage の部品の属性の `valueList`、`webLink.page`。オブジェクトの子 7 種類は `skippedElements` を持たない                                                                                                                            | 高     |
| 4   | Flow だけ派生の情報（`references`）を JSON に持ち、Diff もしている（LWC でなくした形）                                                                                                                                                                                                                  | 中     |
| 5   | 条件の行の形が 7 通りあり、同じ考え（対象のオブジェクト・選択リスト値など）の名前が種類ごとに違う。`kind` のぶつかり（`webLinkTranslation`・`quickActionTranslation` が組織の翻訳とオブジェクトの翻訳で別の形）                                                                                         | 中     |
| 6   | Visualforce・Aura はタグと `{!...}` の集合だけ。中のタグの属性の変化が Diff に出ない                                                                                                                                                                                                                    | 中     |
| 7   | 参照にしていないもの: レコードタイプの選択リスト値・ビジネスプロセス、Flow の変数の `objectType`・動的な選択肢、Aura の `v.` / `c.`。`start.filterFormula` が数式として読まれていない                                                                                                                   | 中     |
| 8   | `analyzeMetadataReferences`・`analyzeCustomLabels` は本番のコードから呼ばれていない（テストだけ）                                                                                                                                                                                                       | 低     |

### 3.2 段階

| 段階 | 内容                                                                                                                                                     | JSON     | 保存の版       |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | -------------- |
| M0   | 今の参照の一覧を出すスクリプトを作り、サンプルのリポジトリで基準にする（以降の段階で参照が減っていないかを確かめる）                                     | 変えない | そのまま       |
| M1   | 共通の走査（`walkMetadataJson`）                                                                                                                         | 変えない | そのまま       |
| M2   | 参照の取り出しを 1 本にし、語彙を 1 つにする（2 本の辺もなくす）                                                                                         | 変えない | そのまま       |
| M3   | Flow の `references` を解析へ移す。3.1 の 3 の消える情報と 7 の参照を足す                                                                                | 変わる   | 上げる         |
| M4   | 数式の JSON（`fx*`。名前・関数・リテラル・演算子・差し込み・テンプレート）。最初は文字列と並べ、使う側を移してから文字列を消す（LWC の段階 2・6 と同じ） | 変わる   | 上げる（2 回） |
| M5   | 条件の行の共通の形と `booleanFilter` の木                                                                                                                | 変わる   | 上げる         |
| M6   | Visualforce・Aura のマークアップを木にする。メール・URL・Flow のテキストテンプレートは `fxTemplate`                                                      | 変わる   | 上げる         |
| M7   | 値の木のうち参照・解析に使うところに `kind` を付ける。名前をそろえる                                                                                     | 変わる   | 上げる         |

数式の JSON の形の案（[metadata-json-review.md](./metadata-json-review.md) 5.1）は、Apex の `FormulaJson`・LWC の `jsBinary` などと同じ考え方（`left`・`operator`・`right`、関数は `name`・`arg`）にする。

## 4. LWC の残り（詳しくは [lwc-json-types.md](./lwc-json-types.md) 8.8）

## 5. 全体の順番

領域をまたいで、次の順に進める案。各段階で、ゴールデン・Diff・依存関係のテストが通る状態にする。

| 順  | 内容                                                          | 段階            | 理由                                                                                                      |
| --- | ------------------------------------------------------------- | --------------- | --------------------------------------------------------------------------------------------------------- |
| 1   | 不具合を直す（JSON を変えない）                               | A0・M0          | 今の出力が正しくなる。M0 の基準は以降の段階の確かめに使う                                                 |
| 2   | 共通の走査の形を決め、メタデータの参照の取り出しを 1 本にする | M1・M2          | 語彙をそろえ、2 本の辺をなくす。Apex・LWC の走査と同じ形にしておく                                        |
| 3   | Apex の式（`kind`・文字列をなくす）と SOSL                    | A1・A2          | Apex の走査（次）の前提                                                                                   |
| 4   | Apex の走査と派生の情報                                       | A3              | 依存関係を JSON の形から切り離す                                                                          |
| 5   | Flow の `references` を解析へ、メタデータの抜け               | M3              | 派生の情報の持ち方を 3 つの領域でそろえる                                                                 |
| 6   | Apex の文・宣言・修飾子・型                                   | A4〜A6          | 文の形を LWC にそろえる                                                                                   |
| 7   | 数式・条件・マークアップの JSON                               | M4〜M6          | いちばん大きい。式の形は Apex・LWC の式に合わせる                                                         |
| 8   | 値の木の型・名前、LWC の型の文字列                            | M7・LWC の 1〜3 | 残りの文字列をなくす                                                                                      |
| 9   | 意味の差分（2 つの時点の解析の結果を比べる）                  | 共通            | 3 つの領域の走査がそろってから作る（[apex-json-analysis.md](./apex-json-analysis.md) 5.2 の `impact.ts`） |

- 保存の版は、同じリリースに入れる段階をまとめて 1 回上げてよい（版は 3 つの領域で共通）。
- 段階ごとに `sourceObject` の数を記録する（LWC の [lwc-json-types.md](./lwc-json-types.md) 8.5 と同じ）。

## 6. 決めたこと（2026-11-10）

次の 10 項目は、すべて案のとおりに決めた。

| #   | 項目                                                                | 決めたこと                                                                                                                                                                      |
| --- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Apex の式の `kind` の名前                                           | 接頭辞なし（`identifier`・`binary` など）。今の Apex の文の `kind`（`if` など）に合わせる。LWC が `js*` なのはテンプレートの `lwc*` とぶつかるため。Apex にはぶつかる相手がない |
| 2   | メタデータの数式の `kind` の名前                                    | `fx*`。Aura の式（`{!v.x}`）も `fx*` にする                                                                                                                                     |
| 3   | Apex の数のリテラル                                                 | 文字列のまま持つ（Long・Decimal の精度を失わないため）。LWC の `jsNumber` は数のまま                                                                                            |
| 4   | Apex の条件を包む `kind`（`ifCondition` など）                      | なくす（LWC と同じ）。GumTree の対応付けが変わるので、サンプルの Diff を比べてから決める                                                                                        |
| 5   | Apex の修飾子の分類                                                 | JSON から消して解析で出す。Diff のレポートが分類を使っているかを先に確かめる                                                                                                    |
| 6   | 読めない数式                                                        | `resolvedError` に出し、その値は文字列のまま残す（構造にできないものを消さないため）                                                                                            |
| 7   | 数式のノードの `sourceKeys`                                         | すべての式のノードに持たせる（LWC と同じ）                                                                                                                                      |
| 8   | `booleanFilter`                                                     | 木だけにする（文字列は持たない。方針 2）                                                                                                                                        |
| 9   | テストだけが使う `analyzeMetadataReferences`・`analyzeCustomLabels` | 依存関係のグラフの上に作り直し、テストをグラフに移す                                                                                                                            |
| 10  | 値の木をどこまで型にするか                                          | 参照・解析に使うところだけ。組織の設定（`settings`）は値の木のまま                                                                                                              |
