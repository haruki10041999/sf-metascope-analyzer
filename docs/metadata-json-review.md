# メタデータの JSON の見直し（調査。LWC・Apex と比べて）

改修方針のまとめは [json-redesign-plan.md](./json-redesign-plan.md)。この文書は 2026-11-10 の調査の結果。

LWC の JS / TS の JSON の見直し（[lwc-json-types.md](./lwc-json-types.md) 5〜8 章）と同じ観点で、メタデータの JSON・処理を調べた。2026-11-10 時点のコード（`SAVE_FORMAT_VERSION` は 7。[parser/commons.ts](../src/analyzer/parser/commons.ts#L49)）。

LWC で決めたこと（比べる基準）:

- 構造の JSON。種類は `kind` で明示する。ソースの文字列は持たない。
- 境界ノード（`kind` と `sourceKeys` を持つ）がはっきりしている。
- 派生の情報（呼び出し・イベント・参照）は JSON に持たず、解析の走査（[walker.ts](../src/analyzer/processor/Lwc/walker.ts)）で出す。
- 本体の Diff は GumTree（[gumtree](../src/analyzer/processor/commons/diff/gumtree/index.ts)）。
- エラーは JSON のノードにしない（`resolvedError` だけ）。

「確かめた」はコードを読んで確かめたもの。動かしてはいない。「未確認」は読んでいないか、読んでも決められなかったもの。

## 0. まとめ

| 観点    | 今の状態                                                                                                                                                                                                                                                                                                                      | いちばん大きい問題                                                                                                                                                       |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1. 形   | 種類ごとの JSON（`kind` あり）と、値の木（[valueTree.ts](../src/analyzer/types/commons/valueTree.ts#L9)。`kind` なし）が混ざる。Flow の要素の中身・ルールの条件・共有先・レポートの条件などは値の木                                                                                                                           | 数式・条件・差し込み（`{!...}`）がすべて文字列のまま。同じ考え（条件の行・選択リスト値・対象の名前）の形と名前が種類ごとに違う                                           |
| 2. 処理 | 参照の取り出しが 4 か所以上（[referenceAnalysis.ts](../src/analyzer/processor/Metadata/referenceAnalysis.ts#L175)・[units.ts](../src/analyzer/processor/dependency/units.ts#L702)・Flow の parse（[flow.ts](../src/analyzer/types/metadata/flow.ts#L302)）・種類ごとの解析）。参照の種類の名前の語彙が 4 つ。共通の走査はない | 同じ参照が 2 本の辺になるところがある。Flow だけ参照を JSON に持つ（LWC で消した形）                                                                                     |
| 3. 抜け | 主な種類の主な値は JSON にある                                                                                                                                                                                                                                                                                                | 依存する選択リスト（`valueSettings`）・FlexiPage の `valueList` は読まずに捨てる（`skippedElements` にも出ない）。オブジェクトの子 7 種類は `skippedElements` を持たない |

段階の案（7 章）: 0 語彙と名前 → 1 共通の走査 → 2 参照の取り出しを 1 本に → 3 Flow の `references` を解析へ → 4 数式の JSON → 5 条件の共通の形 → 6 マークアップ・差し込みの JSON → 7 値の木の大事なところに `kind`。

## 1. 用語

| 用語             | 意味                                                                                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 型の JSON        | `makeXmlJson` / `makeMetadataJson`（[xmlJson.ts](../src/analyzer/types/commons/xmlJson.ts)）で作るもの。`kind` と `sourceKeys` を持つ。境界ノード |
| キーなしの入れ物 | 型はあるが `kind`・`sourceKeys` を持たないもの（`valueSet`・`lookupFilter`・Flow の `edges` など）                                                |
| 値の木           | XML の要素名をそのままプロパティ名にした木（`ValueTree`）。`kind` も `sourceKeys` もない                                                          |
| 値の袋           | 名前 → 文字列の表（FlexiPage の `properties`・Visualforce の `attributes` など）                                                                  |
| 構造を持つ文字列 | 中に文法がある文字列（数式・`booleanFilter`・`{!...}`・URL の差し込み）                                                                           |

### 2.2 文字列のまま持つ構造（いちばん大事なもの）

| 文字列                         | 場所                                                                                            | 今どう読むか                                                                                                                                                                                  | LWC・Apex との違い                                            |
| ------------------------------ | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 数式                           | 項目の `formula`・`defaultValue`、入力規則、ワークフロー、承認、クイックアクション、Flow の数式 | 依存関係を作るときだけ [formula.ts](../src/analyzer/processor/dependency/formula.ts#L72) で字句に分け、名前を拾う（式の木は作らない）                                                         | Apex・LWC は式を JSON（`FormulaJson`・`jsBinary` など）で持つ |
| `{!...}`（Flow）               | Flow のすべての文字列                                                                           | parse のときに XML を正規表現で読み（[flow.ts](../src/analyzer/types/metadata/flow.ts#L285)）、`references` に入れる                                                                          | LWC は解析で出す                                              |
| `{!...}`（Visualforce・Aura）  | マークアップ                                                                                    | 中身を文字列の集合にする（[markup.ts](../src/analyzer/types/metadata/markup.ts#L60)）。解析で正規表現（[referenceAnalysis.ts](../src/analyzer/processor/Metadata/referenceAnalysis.ts#L111)） | LWC のテンプレートは `LwcExpressionJson`                      |
| `{!...}`（メール・ボタン）     | `body`・`subject`・`webLink.url`                                                                | メールは解析で正規表現。ボタンの URL は読まない                                                                                                                                               | 同上                                                          |
| `booleanFilter`・`filterLogic` | リストビュー・参照の絞り込み・FlexiPage・共有・ワークフロー・一致ルール・Flow                   | 読まない（文字列の値として Diff）                                                                                                                                                             | なし（Salesforce だけのもの）                                 |
| 条件の行                       | 上と同じ場所                                                                                    | 形がばらばら（2.3）                                                                                                                                                                           | Apex の `if` の条件は式の JSON                                |

`{!...}` の取り出しは正規表現 `{!([^}]*)}` で、文字列の中の `}` で切れる（`{!IF(a, '}', b)}`）。数式の字句の分け方（[formula.ts](../src/analyzer/processor/dependency/formula.ts#L24)）は文字列・コメントを扱うので、こちらのほうが正しい。

### 2.4 境界ノードと sourceKeys

- 型の JSON はどれも `makeSpanJson`（[spanJson.ts](../src/analyzer/types/commons/spanJson.ts)）で作り、キーの作り方は Apex・LWC と同じ。ここはそろっている。
- `sourceKeys` を持たないところ: 2.1 の「キーなし」と値の木のすべて。参照の位置は、その上の境界ノードになる。例: 参照の絞り込みの項目は項目のノード、Flow の `{!x}` は要素のノード、共有先は共有ルールのノード。LWC は式のノードまで指せる。
- Flow の `edges` は `sourceKeys` を持たない。接続の位置（XML の `connector`）を指せない。
- 数式の中の位置を持たせるには、XML のテキストの位置が要る。今の `XmlElement.text` は実体参照を戻し、前後の空白を除いたもの（[xml.ts](../src/analyzer/types/commons/xml.ts#L11)）なので、文字の位置がソースの位置とずれる。テキストの開始位置と、実体参照の分のずれの表が要る（7 章の段階 4）。
- `skippedElements` を持つのは、オブジェクト・項目・権限・Flow・レイアウト・FlexiPage・ラベル・表の種類。**オブジェクトの子 7 種類（入力規則・レコードタイプ・リストビュー・項目セット・コンパクトレイアウト・ボタン・ビジネスプロセス）は持たない**（[metadata-implementation.md](./metadata-implementation.md) 9 章。objectKey を変えないため）。たとえば `webLink` の `page`（Visualforce のボタン）は読まず、どこにも出ない。
- 入れ子の中で読まない要素は `skippedElements` に出ない（`skippedElements` は直下の子だけ）。3 章の `valueSettings`・`valueList` がこれ。

### 3.2 走査

LWC の `walkLwcJson`（kind ごとの visitor、文脈、`composeLwcVisitors`）に当たるものはない。似たものが 5 つある。

## 5. LWC・Apex に合わせる方針

| 方針                           | LWC・Apex                     | メタデータでの案                                                                                |
| ------------------------------ | ----------------------------- | ----------------------------------------------------------------------------------------------- |
| 構造を持つ文字列は JSON にする | 式は JSON（文字列を持たない） | 数式・条件・差し込みを parse のときに 1 回だけ式の JSON にする                                  |
| 式の種類は `kind` で明示       | `js*`                         | `fx*`（数式。Visualforce の差し込みも数式の言語）。Aura の式は `aura*` か `fx*` を広げる（6.1） |

| 走査は 1 つ                    | `walkLwcJson`                 | `walkMetadataJson`（kind ごとの visitor、文脈はオブジェクト・単位・メンバー）                   |
| 本体の Diff は GumTree         | 文・式                        | 数式・条件の木、マークアップの木                                                                |
| エラーはノードにしない         | `resolvedError`               | 数式が読めないときは `resolvedError`（`FORMULA_SYNTAX`）にし、JSON には文字列を残す（6.2）      |

### 5.1 式の JSON の形の案

Apex の `FormulaJson`（[expression.ts](../src/analyzer/types/apex/expression.ts#L287)）、LWC の `LwcJsBinaryJson` などに合わせる。数式は小さい言語なので、種類は少ない。

| kind（案）                                    | 例                                                                | フィールド（案）                                         | LWC・Apex との対応                                                                  |
| --------------------------------------------- | ----------------------------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `fxName`                                      | `Account.Owner.Name`・`$User.Id`・`$Record.Amount__c`・`v.record` | `path: string[]`（名前の並び。`$` で始まるかで全体変数） | LWC の `jsIdentifier` + `jsMemberAccess` の並び。`lwcDottedNameOf` で作るものと同じ |
| `fxCall`                                      | `ISPICKVAL(Status__c, 'Paid')`                                    | `name`（関数名。大文字にそろえる）、`arg: Expr[]`        | `jsCall`・Apex `MethodCallJson`                                                     |
| `fxString`・`fxNumber`・`fxBoolean`・`fxNull` | `'Paid'`・`100`・`TRUE`・`NULL`                                   | `value`                                                  | `jsString` など                                                                     |
| `fxBinary`                                    | `a > 10`・`a && b`・`a & b`（連結）                               | `left`・`operator`・`right`                              | `jsBinary`・`FormulaJson`                                                           |
| `fxUnary`                                     | `NOT x` は関数、`-x`・`!x`                                        | `operator`・`argument`                                   | `jsUnary`                                                                           |
| `fxParen`                                     | `(a + b)`                                                         | `expression`                                             | `jsParenthesized`                                                                   |

## 6. 気をつけること

### 6.1 言語の違い

- 数式（項目・入力規則・Flow・Visualforce の `{!...}`・メール）は同じ数式の言語。演算子は `&&` / `||` / `&` / `<>` / `==` も使える（未確認: すべての演算子の一覧は Salesforce の文書で確かめる）。
- Aura の `{!...}` は別の言語（`v.` / `c.` / `$Label.c.X`、`?:`、`+`、関数は少ない）。同じ `fxName`・`fxBinary` で表せるが、解決の仕方（`v.` は属性、`c.` はコントローラー）が違う。`{#...}`（一度だけ評価）もある。
- Flow の数式は `{!x}` で資源を指す。`fxMerge` の中の `fxName` が資源の名前か `$Record` かは解析で決める。

### 6.2 読めない数式

- LWC の決まりでは、エラーは JSON のノードにしない。数式が読めないときは `resolvedError` に `FORMULA_SYNTAX` を出し、そのプロパティは文字列のまま持つ案（`formula: string | FormulaJson` にすると使う側が両方を扱う）。もう 1 つの案は、読めない数式は持たない（LWC の読めないファイルと同じ）。ただし数式が消えると Diff が「消えた」に見えるので、文字列を残す案がよい。決める必要がある。

### 6.3 位置

- 2.4 のとおり、テキストの中の位置を出すには `XmlElement` にテキストの開始位置と実体参照のずれが要る（[xml.ts](../src/analyzer/types/commons/xml.ts#L159) の `decodeEntities`）。CDATA の中も同じ。値の木の中の数式（承認の `entryCriteria.formula`）は要素の位置がないので、まず値の木に位置を持たせるか、値の木から型の JSON にする（段階 7）。

### 6.4 objectKey

- 文字列を JSON に変えると、そのノードと上のすべてのノードの `objectKey` が変わる（中身の hash）。保存済みのデータとは比べられないので、`SAVE_FORMAT_VERSION` を上げる。LWC と同じく、段階ごとに 1 つ上げる。
